WEATHERGPT — API & DATA PROVIDER SPECIFICATION

1. Purpose

This document defines how WeatherGPT obtains, validates, normalizes and uses external data.

The fundamental rule is:

THE AI IS NOT THE WEATHER DATA SOURCE.

Weather facts must originate from configured and verified data providers.

The LLM may interpret verified data but must not manufacture missing data.

3. Provider Abstraction

WeatherGPT must use a provider abstraction layer.

The application should not directly depend on provider-specific response formats.

Conceptual interface:

WeatherProvider

* getCurrentWeather()
* getHourlyForecast()
* getDailyForecast()
* getAlerts()
* getHistoricalWeather()

Individual providers implement the interface.

⸻

4. Primary Weather Provider

The primary weather provider must be selected based on:

* API reliability
* Forecast quality
* Geographic coverage
* Free-tier availability
* Rate limits
* Required weather variables
* Licensing
* SIH prototype suitability

The selected provider must be configured through environment variables.

Never hard-code API keys.

⸻

5. Secondary Weather Provider

Where practical, configure a secondary weather provider.

Purpose:

* Provider failure
* Temporary API outage
* Rate-limit protection
* Cross-provider comparison where appropriate

The secondary provider must not automatically override the primary provider simply because its values differ.

Differences must be handled deliberately.

⸻

6. Official Meteorological Information

Official warnings should be obtained from an appropriate official meteorological or disaster-management source where technically and legally available.

Official information must remain separate from:

* WeatherGPT forecasts
* WeatherGPT risk calculations
* AI-generated recommendations

The UI must identify the issuing authority.

Never fabricate an official warning.

Never create a government-looking warning.

⸻

7. Geocoding

WeatherGPT requires location resolution.

Users may provide:

* City
* Town
* Village
* Postal/location name
* Coordinates
* Browser location

The geocoding layer converts human-readable locations into coordinates.

Conceptual result:

Location

* name
* latitude
* longitude
* region
* country

The geocoder must return actual results.

Never invent coordinates.

⸻

8. Browser Geolocation

Browser geolocation may be used only after explicit user permission.

If permission is denied:

Allow manual location search.

Do not silently obtain or expose precise location information.

⸻

9. Air Quality

Air-quality information should come from an actual supported air-quality provider.

Potential fields:

* AQI
* PM2.5
* PM10
* Ozone
* NO2
* Other supported pollutants

If air-quality data is unavailable:

Display:

“Air quality data unavailable.”

Do not estimate AQI using the LLM.

⸻

10. Historical Weather

Historical weather must use an actual historical weather dataset or API.

The system must distinguish:

Historical observations

from

Forecasts

from

Current observations

Historical values must never be generated by the AI.

⸻

11. Climate Data

Climate analysis should use an appropriate historical dataset.

The application must not make climate claims from insufficient data.

Every climate analysis should retain:

* Dataset/source
* Time period
* Location
* Metric
* Calculation methodology

⸻

12. Maps

RiskMap requires a map provider.

The map solution must support the required geographic visualization while respecting:

* Licensing
* API limits
* Attribution requirements
* Performance

Do not use fake map tiles or fake geographic data.

⸻

Potential current variables:

* Temperature

* Humidity
* Pressure
* Wind speed
* Wind direction
* Visibility
* Cloud cover
* Precipitation
* UV index
* Air quality

Potential forecast variables:

* Temperature
* Precipitation probability
* Precipitation amount
* Wind
* Weather condition
* Humidity
* Visibility

Supported conceptual types:

Each provider should have a dedicated adapter.

Example architecture:

17. Validation

Every external response must be validated before use.

Validation should check:

* Required fields
* Data types
* Coordinates
* Timestamps
* Numeric values
* Response structure

Use:

Zod

Invalid responses must not reach the AI layer.

18. Normalization

Provider-specific units and structures must be normalized.

Example:

Provider B temperature

↓

Similarly normalize:

* Wind speed
* Pressure
* Visibility
* Precipitation
* Time
* Coordinates

The internal schema must use clearly documented units.

20. Missing Data

If a provider does not return a value:

Represent it as unavailable.

Example:

visibility: null

Do not replace it with:

* 0
* Average value
* Estimated value
* AI-generated value

unless a documented deterministic derivation is explicitly supported.

⸻

21. API Failure

Possible failures:

* Timeout
* HTTP error
* Invalid JSON
* Rate limit
* Authentication failure
* Provider outage
* Missing data

The system must handle these gracefully.

23. Cache

Weather data may be cached to:

* Reduce API calls
* Improve speed
* Reduce cost
* Improve resilience

Every cache entry must contain:

* Data
* Provider
* Retrieved timestamp
* Expiration time

⸻

24. Cache Freshness

Different data types require different freshness policies.

Current weather should normally be fresher than long-range historical information.

The exact TTL values must be configured centrally rather than scattered throughout the application.

Example configuration concept:

CURRENT_WEATHER_TTL

HOURLY_FORECAST_TTL

DAILY_FORECAST_TTL

ALERT_TTL

HISTORICAL_DATA_TTL

⸻

25. Rate Limits

The application must respect provider rate limits.

Implement:

* Caching
* Request deduplication
* Server-side rate limiting
* Efficient API requests

Never repeatedly call providers unnecessarily for the same request.

⸻

26. API Key Security

All provider keys must remain server-side.

Never expose keys through:

* Client-side JavaScript
* Public environment variables
* GitHub
* Browser network payloads

Use environment variables.

⸻

36. AI Prompt Boundary

The AI prompt must contain structured data.

Example conceptual input:

USER QUESTION:

“Should I travel this evening?”

VERIFIED WEATHER:

Temperature: 29°C

Rain probability: 78%

Wind: 24 km/h

Visibility: 5 km

RISK:

Travel Risk: MODERATE

SUPPORTING FACTORS:

Rain probability

Visibility

The AI should explain this information.

It should not create additional weather values.

⸻

37. AI Grounding Policy

The AI must follow:

1. Use supplied verified information.
2. Never invent missing values.
3. Never invent sources.
4. Never invent warnings.
5. Never invent timestamps.
6. Never claim unavailable forecasts.
7. Never present a prediction as guaranteed.
8. Distinguish observations from forecasts.
9. Distinguish derived risk from official warnings.
10. Admit insufficient information.

⸻

38. Response Validation

Where practical, the generated response should be checked.

Potential checks:

* Numerical values mentioned by AI exist in supplied data.
* Mentioned weather conditions exist in supplied data.
* Mentioned alerts exist in supplied alert data.
* Source claims match actual metadata.

If unsupported claims are detected:

Regenerate or return a safe response.

⸻

39. No-Data Response

When verified information is unavailable:

Example:

“I can’t provide a reliable answer right now because fresh weather data for this location is unavailable.”

This is preferable to an invented answer.

⸻

40. Official Warning Response

If an official warning exists:

The system should clearly identify:

* Warning
* Issuing authority
* Affected area
* Valid time
* Source

The AI may summarize it, but the original meaning must remain intact.

⸻

41. Derived Risk Disclaimer

WeatherGPT-generated risk should be labelled as:

“WeatherGPT assessment”

or equivalent.

It must not be labelled:

“Official warning”

unless the information actually originates from an official authority.

⸻

42. Recommendation Boundary

WeatherGPT may provide weather-informed recommendations.

Examples:

“Consider carrying rain protection.”

“Consider postponing outdoor activity.”

“Conditions may make travel more difficult.”

Recommendations are advisory.

They must not be presented as guaranteed outcomes.

⸻

43. API Observability

Track:

* Request ID
* Provider
* Response status
* Latency
* Cache status
* Error type

Never log:

* API keys
* Passwords
* Authentication secrets
* Unnecessary personal data

⸻

44. Provider Health

The backend should be able to detect provider problems.

Useful internal metrics:

* Success rate
* Error rate
* Response latency
* Rate-limit events
* Data freshness

This improves reliability.

⸻

45. Testing Requirements

Each provider adapter must have tests for:

* Valid response
* Missing field
* Invalid field
* Invalid timestamp
* Provider error
* Rate-limit response

The normalized output must be tested independently of the provider.

⸻

46. Mock Data Policy

Mock data may be used during development and automated testing.

However:

Mock data must be clearly identified.

Mock data must never accidentally appear as real production weather.

Do not create fake “live” indicators using mock data.

⸻

47. Prototype Data Policy

For the SIH prototype:

Real APIs should be used wherever practical.

If a feature cannot be connected to a real provider:

1. Clearly mark it as unavailable, or
2. Demonstrate it using explicitly labelled demo data.

Never present fabricated data as live information.

⸻

48. Provider Selection Rule

The development agent must not arbitrarily choose an API provider and hard-code it.

Before implementation, the provider must satisfy:

* Required coverage
* Required variables
* Acceptable rate limits
* Acceptable licensing
* Secure API access
* Sufficient reliability
* Compatibility with the SIH demonstration

Provider choice must be documented.

⸻

49. Data Source Priority

When multiple sources exist, prefer:

1. Appropriate official source for official warnings.
2. Reliable meteorological provider for weather forecasts/observations.
3. Appropriate historical dataset for historical analysis.
4. Derived WeatherGPT calculations.
5. AI interpretation.

Never reverse this hierarchy.

⸻

50. Final Data Integrity Rule

WeatherGPT must always prefer:

VERIFIED INFORMATION

over

COMPLETE INFORMATION

If only part of the required information is available, provide the verified portion and clearly state what is unavailable.

Never fill gaps with imagination.
